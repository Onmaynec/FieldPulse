# Архитектура FieldPulse

## Компоненты

API на FastAPI реализует серверную проверку прав, статусы, заявки, договоры, SLA, синхронизацию и акты. PostgreSQL — транзакционный источник истины. SILO — закрытое S3-совместимое хранилище фотографий, отдаваемых только через проверяющее права API. Worker раз в 15 секунд догоняет дедлайны и заносит события с уникальными ключами в журнал и mock inbox. PWA хранит оболочку в Service Worker, а рабочие карточки и очередь действий — в IndexedDB.

## Основные сущности

Organizations → Sites → Assets. Для сайта хранится Contract с календарём и набором SLA-политик. Ticket содержит объект, оборудование, исполнителя, статус, версию, дедлайны и снимок политики на момент создания. Event фиксирует события append-only на уровне API. Worklog содержит UUID действия, server_at, client_at, материалы и чек-лист. Attachment имеет checksum, владельца и приватный ключ хранилища. Act хранит номер редакции, статус и решение клиента.

## Конкуренция

При смене статуса и назначения используется `SELECT FOR UPDATE` и проверка ожидаемой версии. Для синхронизации действует уникальное ограничение `(engineer_id, action_uuid)`. Конфликт возвращается как отдельный результат без перезаписи. Время хранится в UTC, календарь рассчитывается по зоне объекта. Изменение глобальной политики SLA не меняет уже созданный снимок в заявке.

SSE передаёт событие доски без закрытых данных. Для чтения подробностей клиент использует авторизованный API. Фактический срок реакции определяется моментом принятия инженером, а не моментом назначения.

## Хранение фотографий и транзакции

Загрузка в SILO и запись транзакции PostgreSQL не являются единой атомарной операцией. `save_image` теперь компенсирует частичный upload: если исходник записан, а миниатюра не загрузилась, исходник удаляется. `mobile.sync` и прямой upload удаляют уже загруженные объекты, если соответствующая транзакция БД откатилась. Это покрывает обработанные ошибки и rollback, но не жёсткое завершение контейнера/процесса между успешным PUT и commit. В таком случае объект-сирота всё ещё возможен; периодический reconciliation ключей с таблицей `attachments` остаётся отдельной задачей.

## Резервная копия и восстановление

`app.backup` создаёт ZIP с PostgreSQL custom dump, объектами `tickets/` и SHA-256 манифестом. PostgreSQL dump использует собственный MVCC snapshot, но S3 перечисляется и читается отдельно. Поэтому cross-store consistency требует остановить API, worker, monitor и любые внешние writers на время создания архива. `--maintenance-confirmed` — осознанное подтверждение оператора, не распределённая блокировка записи.

Восстановление разрешено только в пустую базу и пустой bucket. PostgreSQL восстанавливается с `--exit-on-error` и `--single-transaction`; затем сверяются таблицы и ревизия Alembic. S3-объекты загружаются по одному и сразу проверяются чтением и SHA-256. Между PostgreSQL и S3 нет общей транзакции: после частичного сбоя recovery-контур уничтожается и создаётся заново.

`scripts/recovery_probe.py` делает исходный снимок количества строк каждой таблицы, ревизии Alembic, метаданных Attachment и хешей всех объектов. После restore он сравнивает их и проверяет API-права на восстановленном контуре. Проверка ролей выполняется после сравнения, потому что успешные входы добавляют записи аудита авторизации.

## PWA и офлайн-данные

Для инженера локально сохраняется только минимальная идентичность `id/name/role`; пароль и cookie-сессия в localStorage не записываются. Это позволяет открыть уже загруженные карточки после перезапуска браузера без сети, но не даёт права выполнять серверные операции без действующей сессии. Очередь действий и фотографии остаются в отдельной IndexedDB инженера.

Обновление кеша карточек выполняется одной read/write-транзакцией `dbReplaceAll`: `clear` и все `put` завершаются вместе. При quota error предыдущий полный кеш остаётся на месте. Ошибка обновления списка не блокирует попытку отправить ранее сохранённую очередь. Успешная отправка удаляет запись только после ответа сервера; сетевые ошибки и неполные ответы оставляют запись в очереди с кодом ошибки и числом попыток.

Браузерная Storage API может разрешить persistent storage по явному нажатию инженера. Это снижает риск автоматической очистки, но не гарантирует сохранность при очистке профиля, удалении сайта, повреждении диска или сбросе устройства. Локальные данные не шифруются приложением.

## Нагрузочный профиль

`scripts/load_profile.py` поддерживает burst и paced режим до 168 часов. В paced режиме заявки распределяются равномерно по длительности, фотографии создаются с заданным размером/качеством JPEG. Отчёт фиксирует p50/p95 операций, ошибки, фактический размер фото, CPU, память, диск и параметры PostgreSQL. Запуск не удаляет созданные данные и предназначен только для отдельной demo/staging базы.

## Компромиссы

Тесты SQLite не заменяют параллельные тесты PostgreSQL. Автоматический 48-часовой тест на реальном устройстве и полноценный 24-часовой профиль не могут считаться выполненными по короткому CI. Для них предусмотрены воспроизводимые инструкции и отчёт, но результаты должны поступить с целевого стенда.
