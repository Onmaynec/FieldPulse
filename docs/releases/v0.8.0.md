# FieldPulse v0.8.0 — Recovery & Data Integrity

В v0.7.0 появились инциденты SLA и короткие профили PostgreSQL. В v0.8.0 я сосредоточился на восстановлении данных, поведении мобильного приложения после перезапуска браузера и конкурентных операциях, где две параллельные команды могут прийти к одной записи.

## Резервная копия и восстановление

- `app.backup create` теперь требует явный флаг `--maintenance-confirmed`. Это не автоматическая блокировка, а подтверждение того, что оператор остановил API, worker, monitor и внешних writers.
- В документации уточнено ограничение snapshot: `pg_dump` даёт согласованный снимок PostgreSQL, но перечисление и чтение объектов S3 не участвуют в той же транзакции. Без окна обслуживания возможен рассинхрон между строками БД и фотографиями.
- Restore принимает только чистую БД без прикладных таблиц и пустой bucket. `pg_restore` запускается с `--exit-on-error` и `--single-transaction`.
- После восстановления сверяются все таблицы и ревизия Alembic. Каждый объект S3 повторно читается и проверяется по SHA-256.
- Новый `scripts/recovery_probe.py` сравнивает полный снимок таблиц, ролей, Attachment и S3-объектов; проверяет доступ владельца вложения и отказ для другого клиента.
- Compose получил изолированный recovery-проект: отдельные PostgreSQL, SILO, API, tool-контейнер и внутреннюю сеть. Рабочие тома не затрагиваются.
- CI проверяет, что усечённый ZIP отклоняется до restore, и сохраняет архив/отчёт как артефакт.

## Фотографии и rollback

- Если загрузка миниатюры не удалась после исходного изображения, приложение пытается удалить уже записанный исходник.
- Если загрузка изображения завершилась, но транзакция БД откатилась, `mobile.sync` и прямой upload удаляют уже загруженные объекты.
- При конфликте одинакового UUID на разных заявках уникальное ограничение `(engineer_id, action_uuid)` остаётся последним арбитром. `IntegrityError` после rollback преобразуется в `duplicate` или `conflict`, а не в HTTP 500.
- Удаление объекта — best effort. Жёсткое завершение процесса между PUT и commit всё ещё может оставить сироту; автоматическая очистка сирот не заявляется как реализованная.

## Конкурентные сценарии

В `scripts/concurrency_smoke.py` добавлены PostgreSQL-сценарии:

- Одновременные назначение и отмена одной заявки с одинаковой версией — один переход проходит, второй получает 409.
- Одинаковый UUID на двух разных заявках одного инженера — создаётся только один Worklog и один комплект вложений, второй запрос становится конфликтом.
- Два решения одного акта — одно фиксируется, второе получает 409; при возврате создаётся следующая draft-редакция.
- Два параллельных прохода SLA-worker — для одной просроченной заявки остаётся по одному событию реакции и устранения, с соответствующими outbox-записями.

Это тесты реального PostgreSQL в изолированном Compose, а не SQLite-модель блокировок.

## PWA и долгий офлайн

- Минимальная идентичность инженера (`id/name/role`) сохраняется в localStorage, чтобы после закрытия браузера и отключения сети снова показать ранее загруженные карточки. Пароль и сессионный токен не сохраняются.
- IndexedDB обновляет список карточек атомарно: старый кеш не очищается до завершения новой транзакции.
- Инженер может запросить persistent storage через Storage API. Решение остаётся за браузером; интерфейс показывает использование и доступную квоту.
- Ошибка обновления списка карточек больше не блокирует отправку уже сохранённых действий. Очередь хранит число попыток и код последней ошибки, а запись удаляется только после подтверждения сервера.
- Browser E2E закрывает браузерный процесс, открывает тот же профиль офлайн и проверяет сохранение очереди с фотографиями.

## Суточная нагрузка

`scripts/load_profile.py` получил paced-режим до 168 часов и параметры JPEG. В отчёт включены p50/p95, количество ошибок, реальный размер изображения, CPU, память, диск и настройки PostgreSQL. Для целевого сценария предусмотрен запуск 200 заявок и 1000 фотографий за 24 часа.

Сам 24-часовой прогон и 48-часовое отключение сети на физическом устройстве не объявлены выполненными: CI проверяет короткий режим и один полный перезапуск браузера. Для этих двух критериев нужен отдельный стенд и фактический отчёт с целевого устройства.

## Обновление

Перед обновлением проверьте резервную копию PostgreSQL и S3, затем выполните:

    git pull origin main
    docker compose up -d --build

Новая версия не меняет формат API mobile sync и не удаляет локальную очередь. При первом открытии обновлённый Service Worker заменит кеш оболочки. Не очищайте данные сайта, пока все черновики не синхронизированы.
