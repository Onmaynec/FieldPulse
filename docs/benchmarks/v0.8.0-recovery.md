# v0.8.0 — протокол восстановления и длительной нагрузки

## Что проверяет CI

Job `compose-smoke` выполняет последовательность на отдельной тестовой инфраструктуре:

1. Создаёт demo-данные, заявки и фотографии.
2. Завершает обычные браузерные, мобильные и конкурентные сценарии.
3. Останавливает `api`, `worker` и `monitor`.
4. Снимает исходный отчёт: все таблицы, ревизия Alembic, роли, связи `Attachment` и SHA-256 каждого S3-объекта.
5. Создаёт ZIP `pg_dump` + S3 и проверяет его манифест.
6. Усекает копию ZIP и требует, чтобы verifier отказал.
7. Поднимает отдельный Compose-проект `fieldpulse-recovery` с чистыми PostgreSQL и SILO.
8. Восстанавливает архив, проверяет схему, строки и все хеши объектов.
9. Запускает API восстановленного контура и проверяет доступ администратора, инженера и двух клиентских организаций.

Артефакт GitHub Actions: `fieldpulse-v08-recovery-drill`. В нём сохраняются `source.json`, полный backup ZIP и усечённая копия. В архиве могут находиться демо-данные и фотографии, поэтому доступ к артефакту ограничивается политикой репозитория.

## Критерии успеха

- Все прикладные таблицы присутствуют, количество строк совпадает с исходным отчётом.
- Ревизия Alembic совпадает.
- Все записи Attachment совпадают по ID, ticket, organization, ключам оригинала и миниатюры, checksum и размеру.
- Для каждого ключа `tickets/` SHA-256 и byte count совпадают после чтения из восстановленного S3.
- Владелец вложения получает 200; другой клиент получает 404.
- Роль admin получает доступ к operations summary; engineer получает 403.
- Повреждённый архив не проходит `verify`.

Числовые количества и итоговые CI-ссылки вносятся после успешного выполнения актуального workflow. Само наличие сценария не является подтверждением пройденного restore drill.

## Конкурентность

`concurrency_smoke.py` использует реальные API-запросы и PostgreSQL row locks. Проверяются гонка assign/cancel, cross-ticket UUID uniqueness, параллельные решения акта и параллельные `run_once` двух SLA-worker. Сценарий создаёт тестовые заявки и события, поэтому запускать его только на demo/staging.

## Профиль 24 часа

Для фактического профиля предусмотрен запуск:

    python scripts/load_profile.py --tickets 200 --photos-per-ticket 5 --workers 4 --duration-hours 24 --photo-width 1600 --photo-height 1200 --photo-quality 86 --allow-writes --output /tmp/fieldpulse-24h.json

200 заявок распределяются равномерно по 24 часам, по 5 JPEG на каждую. Отчёт включает p50/p95, throughput, ошибки, размер JPEG, CPU, память, диск и параметры PostgreSQL. Скрипт не удаляет созданные данные. Не запускать на production; заранее проверить свободное место и лимиты S3.

Результат можно считать 24-часовым только при `elapsed_seconds >= 86400`, `failed_tasks == 0`, 200 завершённых заявках и 1000 завершённых фотографиях. Если профиль остановлен раньше, это короткий прогон, а не выполненный критерий.

## Профиль 48 часов без сети

Автоматизированный CI закрывает Chromium, повторно открывает тот же профиль без сети, проверяет локальную идентичность, карточки и IndexedDB очередь, затем восстанавливает соединение и сверяет серверные worklog/attachments. Это проверка перезапуска, но не 48-часовой endurance test.

Для 48 часов требуется реальный Android/Windows планшет или телефон, выбранный браузер и профиль, который будет использоваться на объекте. Протокол: предварительная загрузка карточек, запрос persistent storage, отключение сети, создание работ и фото, полное закрытие браузера, ожидание 48 часов, повторный offline start, сверка очереди, затем reconnect и серверная проверка без дублей. Нужно сохранить модель устройства, версию ОС/браузера, время начала/окончания, квоту/использование storage и итоговую сверку. Без такого отчёта критерий остаётся открытым.

## Ограничения

- Восстановление PostgreSQL и S3 не атомарно; при частичном сбое disposable target следует уничтожить и создать заново.
- Stop API/worker/monitor не блокирует сторонних writers; перед backup оператор обязан остановить все источники изменений.
- Приложение не шифрует локальную IndexedDB.
- Сценарии synthetic JPEG и GitHub-host не дают production SLO.
