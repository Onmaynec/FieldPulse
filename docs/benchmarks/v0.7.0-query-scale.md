# FieldPulse v0.7.0 — нагрузка SQL на 50k и 200k заявок

## Метод

CI запускает независимый PostgreSQL 16 и актуальные миграции, создаёт 2000 демо-заявок и добавляет 50 000, а затем 200 000 синтетических строк в отдельной **незавершённой транзакции**. Каждая серия выполняет по три реальных `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` для сортировок `newest`, `deadline`, `priority` на первой и глубокой OFFSET-странице, а также на сопоставимой keyset-странице. Измеряется и поиск по подстроке.

В выходных `fieldpulse-50k.json` и `fieldpulse-200k.json` должны присутствовать размер набора, фактический OFFSET, версия PostgreSQL, число CPU, наличие pg_trgm, планы с использованными индексами, буферные чтения, серверное время и клиентские p50/p95. Клиентское время включает стоимость получения плана EXPLAIN, а не HTTP-запрос.

После завершения каждого профиля проверяется, что постоянная тестовая база вновь содержит ровно 2000 записей. Вся среда удаляется после CI; на рабочей базе тест не запускается.

## Результаты и интерпретация

Числовой результат и вывод об ускорении можно зафиксировать только после успешного CI и просмотра артефакта `fieldpulse-v07-query-scale`. Если профили не прошли или результат не сохранился, это остаётся непроверенным критерием.

Нагрузка синтетическая, на одном GitHub-host, с тремя повторениями. Это **не** суточный production SLO, не многопользовательский профиль и не проверка сетевой передачи фотографий. Для серьёзного capacity planning потребуется длительный прогон на целевом железе и реальных пропорциях данных.


## Фактически выполненные профили — 14 ноября 2026

Подтверждено двумя отдельными CI-запусками, а не предполагаемыми цифрами. Первый запуск до индекса `ix_ticket_created_seek` — [Actions #43566701075](https://github.com/Onmaynec/FieldPulse/actions/runs/43566701075), артефакт `fieldpulse-v07-query-scale`. Второй после добавления индекса — [Actions #43567014842](https://github.com/Onmaynec/FieldPulse/actions/runs/43567014842), одноимённый артефакт.

Окружение обоих: Linux GitHub Actions, PostgreSQL **16.16**, **4 vCPU**, `pg_trgm` доступен. Для каждого профиля выполнялось **3 измерения**; таблица ниже отражает **p95 времени клиентского вызова EXPLAIN ANALYZE**, в миллисекундах. Она **не отражает** отдельные HTTP-задержки. Данные были некоммитнутыми и полностью откатились; контроль БД подтвердил возврат к 2000 seed-заявкам.

Глубина OFFSET — **26 000** для 52k и **101 000** для 202k. После обновления PostgreSQL выбрал B-Tree `ix_ticket_created_seek` на всех трёх вариантах сортировки newest, `ix_ticket_deadline_seek` для deadline и `ix_ticket_priority_seek` для priority. На старом плане newest соответствующего индекса не было.

Поиск подстроки `benchmark` после индекса дал p95 **2,82 мс** на 52k и **4,01 мс** на 202k. Это специфичный синтетический запрос с совпадениями в тестовых данных, **не** доказательство общей эффективности полнотекстового поиска для произвольных терминов.

### Ограничения сравнения

GitHub Actions не гарантирует, что два workflow исполняются на одном физическом хосте. Прогоны выполнялись с прогревом и тремя повторениями, а якорь курсорной страницы определялся отдельным запросом, не включённым в измеряемое время keyset. Снижение задержек подтверждается конкретными планами и числами этих прогонов, но не распространяется автоматически на продуктивную БД.

Натурный 24-часовой профиль, конкурирующие пользователи, большие фото и independent restore drill остаются отдельными приёмочными работами.
