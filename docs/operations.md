# Эксплуатация и восстановление

Проверка контейнеров: `docker compose ps`. Логи: `docker compose logs -f api worker monitor`. Health: `/health/live` и `/health/ready`. API записывает JSON-логи с correlation ID, маршрутом, кодом ответа и задержкой.

Миграции: `docker compose run --rm migrate`. Для следующей версии добавить отдельную Alembic-ревизию. Наполнение: `docker compose run --rm seed` (не пересоздаёт существующие данные).

## Резервная копия PostgreSQL и S3

Полный архив создаётся только в окно обслуживания. PostgreSQL `pg_dump` использует согласованный MVCC snapshot, но список и чтение объектов S3 не входят в ту же транзакцию. Чтобы получить согласованную копию двух хранилищ, остановите все процессы, способные менять заявки или фотографии. Внешние интеграции и другие writers также должны быть остановлены.

На машине, где запущен Compose:

    mkdir -p .recovery
    docker compose stop api worker monitor
    docker compose --profile maintenance run --rm backup-tool python -m scripts.recovery_probe snapshot /backups/source.json
    docker compose --profile maintenance run --rm backup-tool python -m app.backup create /backups/fieldpulse-backup.zip --maintenance-confirmed
    docker compose --profile maintenance run --rm backup-tool python -m app.backup verify /backups/fieldpulse-backup.zip

Файлы появятся в `.recovery/`. `source.json` содержит количества всех таблиц, ревизию Alembic, метаданные вложений и SHA-256 всех объектов `tickets/`. Он нужен для последующей проверки восстановления. ZIP содержит custom dump PostgreSQL и сами объекты; манифест проверяет размер и SHA-256 каждого участника.

`--maintenance-confirmed` — явное подтверждение оператора, а не автоматическая блокировка записи. Команда не останавливает API и не блокирует внешних writers самостоятельно. Если приложение или другой клиент пишет в БД/S3 во время копирования, точка времени между PostgreSQL и объектами может разойтись. Не запускайте backup-tool без остановки writers.

После завершения копирования можно вернуть рабочие процессы:

    docker compose start api worker monitor

Не перезаписывайте существующий архив: команда `create` откажется перезаписывать целевой файл. Для следующего снимка используйте новое имя или перенесите предыдущий архив в безопасное место.

## Восстановление в отдельный чистый контур

Восстановление не запускайте поверх действующей рабочей базы. Новый проект Compose поднимает собственные PostgreSQL и SILO, использует отдельную внутреннюю сеть и именованные тома:

    docker compose -p fieldpulse-recovery --profile recovery up -d recovery-postgres recovery-minio
    docker compose -p fieldpulse-recovery --profile recovery run --rm recovery-tool python -m scripts.recovery_probe init-bucket
    docker compose -p fieldpulse-recovery --profile recovery run --rm recovery-tool python -m app.backup restore /recovery/fieldpulse-backup.zip --confirm-empty
    docker compose -p fieldpulse-recovery --profile recovery up -d recovery-api
    docker compose -p fieldpulse-recovery --profile recovery run --rm recovery-tool python -m scripts.recovery_probe verify /recovery/source.json

В `.recovery/` должны находиться `fieldpulse-backup.zip` и `source.json`. Восстановитель до первой записи проверяет пустую базу и bucket. `pg_restore` выполняется с `--exit-on-error` и `--single-transaction`; после него сверяется схема и читаемость таблиц. Каждый объект S3 повторно читается и сверяется по SHA-256. Финальный probe сравнивает количество строк всех таблиц, ревизию Alembic, связи вложений, байты и хеши всех объектов; затем проверяет роли: администратор получает доступ к операциям, инженер — отказ, владелец вложения — доступ, другой клиент — 404.

PostgreSQL и S3 не образуют общую транзакцию. Если восстановление прервалось после PostgreSQL или после части объектов, не продолжайте на том же контуре. Удалите только отдельный recovery-проект и его тестовые тома, создайте новый пустой контур и повторите проверку:

    docker compose -p fieldpulse-recovery --profile recovery down -v --remove-orphans

Эта команда удаляет тома **только проекта `fieldpulse-recovery`**. Не добавляйте `-v` к обычному рабочему `docker compose down`: это удалит рабочие тома.

После успешной проверки перенос восстановленного контура в production выполняется отдельным планом переключения. Сам тестовый проект не публикует порты и не переключает рабочую инсталляцию автоматически.

## Повреждённые архивы и частичные загрузки

`verify` проверяет ZIP-структуру, список членов и SHA-256 до начала восстановления. CI также создаёт усечённую копию архива и проверяет, что она отклоняется. При загрузке фотографии ошибка на втором объекте (миниатюре) приводит к попытке удалить уже записанный исходник. Если транзакция БД откатывается после успешной загрузки изображений, приложение удаляет загруженные объекты. При аварийном завершении процесса до cleanup могут остаться сиротские ключи; автоматический сборщик сирот пока не реализован.

## Диагностика

Если API не видит базу — проверить `postgres` и `DATABASE_URL`. При ошибке 503 фото — проверить MinIO/SILO и `S3_*` параметры. При задержке SLA-событий — статус `worker`, таблицы `events` и `outbox`. Если синхронизация вернула конфликт, данные остаются в IndexedDB и должны быть разобраны вручную.

## v0.8.0 — конкурентность и длительные проверки

PostgreSQL smoke запускается внутри API-контейнера:

    docker compose exec -T api python -m scripts.concurrency_smoke

Сценарий проверяет гонку назначения/отмены одной заявки, повтор UUID на двух разных заявках одного инженера, одновременное решение одного акта и два параллельных прохода SLA-worker. Это короткая проверка на реальном PostgreSQL; она не заменяет многосуточный тест производственной нагрузки.

Суточный профиль для изолированной тестовой среды (200 заявок, 5 фотографий на каждую, 4 worker-потока, 24 часа, JPEG 1600×1200):

    docker compose exec -T api python scripts/load_profile.py --tickets 200 --photos-per-ticket 5 --workers 4 --duration-hours 24 --photo-width 1600 --photo-height 1200 --photo-quality 86 --allow-writes --output /tmp/fieldpulse-24h.json

Затем скопируйте отчёт: `docker cp "$(docker compose ps -q api):/tmp/fieldpulse-24h.json" ./fieldpulse-24h.json`. Скрипт распределяет создание заявок равномерно по заданному времени и записывает p50/p95, число ошибок, фактический размер фото, CPU, память, диск и параметры PostgreSQL. Запуск создаёт реальные заявки и S3-объекты; автоматического удаления нет. На production не запускать.

48-часовую офлайн-проверку проводят на реальном целевом устройстве и в одном браузерном профиле: войти инженером, загрузить карточки, разрешить постоянное хранение, отключить сеть, создать черновики с фотографиями, полностью закрыть браузер и оставить устройство без сети на 48 часов. После повторного открытия проверить карточки и очередь до включения сети; затем подключить сеть, синхронизировать и сверить worklog/attachments на сервере. CI проверяет один перезапуск браузера, но не 48 часов реального простоя. Хранилище браузера не зашифровано приложением; устройство должно быть защищено средствами ОС.

## Контур v0.7.0

`monitor` работает отдельно от `worker`, проверяет heartbeat каждые 15 секунд, открывает инцидент при `error`/`stale` и закрывает после подтверждённого `healthy`. `ALERT_WEBHOOK_URL` необязателен. Если PostgreSQL или Docker-хост недоступен, этот же контур не сможет записать инцидент или отправить webhook; внешний мониторинг инфраструктуры остаётся необходимым.

## Безопасность эксплуатации

Демо-аккаунты предназначены только для локального запуска. Перед публикацией в Интернете задайте случайные секреты, включите HTTPS и `COOKIE_SECURE=1`, ограничьте доступ к MinIO console и к портам PostgreSQL. Резервные архивы содержат персональные и рабочие данные: шифруйте их на уровне носителя/хранилища, ограничивайте права и проверяйте срок хранения.
